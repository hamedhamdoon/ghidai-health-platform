## Database and host runtime evidence

Read-only verification on 2026-10-15: `compose.yaml` pins both local databases to `postgres:17.6-alpine@sha256:ef257d85f76e48da1c64832459b59fcaba1a4dac97bf5d7450c77753542eee94` (the integrator also observed running server 17.6); `node --version` returned `v24.20.0`. A digest makes the image reproducible, not current or vulnerability-free. Neither image/container/volume nor host runtime was changed during this review.

The [official PostgreSQL version table](https://www.postgresql.org/support/versioning/) currently lists **17.11** as the current supported 17.x patch (17.x supported through 2029-11-08). Thus 17.6 is five patch releases behind. The [17.11 release notes](https://www.postgresql.org/docs/release/17.11/) date it 2026-08-13 and describe required review of configuration/data cleanup and possible extension reindexing. In particular, CVE-2026-14666 corrects stale cached plans after role changes that can affect RLS; this is directly relevant to a pooled, role-sensitive application. Other fixes cover server memory safety and dump/restore clients. The [official PostgreSQL 17 security table](https://www.postgresql.org/support/security/17/) identifies fixes including pg_dump CVE-2026-19385 and psql CVE-2026-18408 in 17.11. Existing 17.6 synthetic RLS/restore success does not prove those engine defects absent. **Production PostgreSQL/server-client patch acceptance is BLOCKED** pending an isolated current-patch rehearsal.

The current [official Node 24.22.0 LTS release](https://nodejs.org/en/blog/release/v24.22.0) is dated 2026-10-14, so local 24.20.0 is behind two 24.x minor releases while remaining in the supported 24.x line. Separately, the [official announcement updated 2026-10-14](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases) announces HIGH-severity fixes for 24.x on or shortly after **2026-10-21**. As of this review those future fixes and detailed affected-feature/CVE information were not yet released; no future fixed version or current application exploitability is claimed. Production runtime security acceptance remains **OPEN/BLOCKED** until current LTS compatibility is tested and the announced security release is reassessed before launch. No machine-wide Node update was attempted.

Safe next acceptance work: verify a current official PostgreSQL image and digest, scan its OS/native packages (including Alpine/OpenSSL) and separately assess the Docker host/Desktop version; none of those container/host scans has been executed here. Use an additional isolated synthetic cluster and matching updated pg_dump/pg_restore/psql clients, restore a verified encrypted backup, inspect required extension/configuration actions, then rerun full role/RLS/pooling/auth/migration/backup-restore/outage regression.
